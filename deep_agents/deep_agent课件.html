Deep Agents：让 Agent 胜任“长周期、复杂任务”

Claude Code、Deep Research、Manus 等产品可长时间运行并完成大量工具调用。其共性在于一套可复用的工程结构。
Deep Agents 把这套套路抽象成了一个开箱即用的 Agent Harness：规划、文件系统、子agent、上下文压缩、长期记忆。

01

为什么需要 Deep Agent？

The ceiling of Shallow Agents

Shallow Agent 指最常见的“LLM + 工具调用”循环（ReAct 循环）：模型思考 → 调工具 → 看结果 → 再思考，所有信息都堆在同一条消息历史里。

Shallow Agent 的“天花板”

① 受限于上下文窗口

完全依赖 LLM 有限的上下文作为“记忆”和“工作区”，信息一多就被遗忘或截断。

② 难以聚焦，容易偏航

对话越长模型越“健忘”，在大量无关信息中忘记最初的任务目标（lost in the middle）。

③ 缺乏规划与容错

没有系统性的计划、回溯和调整，一旦走上错误路径很难自行纠正。

④ 无法规模化

通常只能胜任 5~15 步的短任务；需要数百步的长周期项目基本做不下来。
关键洞察：瓶颈常不在模型能力上限，而在于缺乏对工作记忆与任务结构的管理。更强模型可抬高上限，但无法消除该结构瓶颈；Deep Agent 解决的是工程结构问题。

03

快速上手：三个参数跑起来

What you get beyond your tools

Deep Agents 默认就带了一套更适合复杂任务的 agent loop。你只需要提供模型、工具、系统提示词：

# pip install -qU deepagents langchain-openai
from deepagents import create_deep_agent

def get_weather(city: str) -> str:
    """Get weather for a given city."""
    return f"It's always sunny in {city}!"

agent = create_deep_agent(
    model="openai:gpt-5.4",          # 也可以传入 ChatModel 实例
    tools=[get_weather],             # 你的业务工具
    system_prompt="You are a helpful assistant",
)

result = agent.invoke(
    {"messages": [{"role": "user", "content": "what is the weather in sf"}]}
)
print(result["messages"][-1].content)

模型到底多带了什么？

仅传入 get_weather 时，harness 仍会默认挂载文件系统与子代理。先建立「默认 / 可选」心智模型，再展开具体工具。

默认

  • 文件系统：笔记、报告与大结果外置存储，按需回读
  • 子代理 task：委派繁杂子任务，主 agent 仅接收结论

另含 Summarization、PatchToolCalls 与提示词缓存等辅助能力，下一节拆中间件栈时再述。

可选

  • 规划 write_todos：v0.7+ 不再默认，要显式 TodoListMiddleware()
  • memory= / skills=：常驻偏好 vs 按需技能
  • interrupt_on / permissions=：人工审批与路径级权限
能力要点
默认文件工具（含 delete※）· task外置工作区 + 委派
可选write_todos长任务再挂 TodoList
可选memory / skills / HITL / permissions记忆、技能、审批、路径权限

※ delete 需 deepagents≥0.7；后端不支持删除时，工具会自动隐藏。沙箱后端才有 execute。

说明：返回的 agent 为已编译的 LangGraph 图，可直接使用 invoke / stream / checkpointer。
04

整体架构：基于中间件的 Harness

Middleware stack

create_deep_agent 本质上是 LangChain 1.x 的 create_agent + 一组预置中间件。每一项能力都是一个可替换、可关闭的中间件。

设计哲学：“能力 = 中间件”。中间件可以注入系统提示词、注册工具、改写模型请求、拦截工具结果。因此既可采用默认配置，也可逐项替换或关闭。
05

能力一：规划与执行（可选）

Opt-in planning · TodoListMiddleware
v0.7 变更：任务规划改为 opt-in。需要待办清单时，显式传入 TodoListMiddleware；未开启则没有 write_todos。
from deepagents import create_deep_agent
from langchain.agents.middleware import TodoListMiddleware

agent = create_deep_agent(
    model="openai:gpt-5.4",
    middleware=[TodoListMiddleware()],  # 开启后才有 write_todos
)

开启后，write_todos 不调用外部系统，只将待办清单写入 agent 的状态（state）。

有效原因：

  • 强制先想后做：开始前先把大任务拆成可执行步骤；
  • 对抗遗忘：每次更新清单，计划会重新出现在上下文末尾，目标保持可见；
  • 动态调整：发现新信息后可以增删改步骤，支持回溯纠错；
  • 可观测：前端可实时展示进度，便于跟踪 agent 当前步骤。
类比：大型任务启动前列 checklist，完成后逐项勾销。

能力二：文件系统，外部化的工作记忆

Filesystem & Backends

上下文窗口容量有限且成本高；文件系统可承载更大工作区。Deep Agent 使模型将信息写入文件并按需回读。

文件工具

工具用途
ls列出目录
read_file按行分页读取（支持 offset / limit）
write_file新建 / 覆盖文件
edit_file精确字符串替换（与 Claude Code 风格一致）
delete删除文件或目录（deepagents≥0.7；后端不支持则自动隐藏）
glob / grep按模式找文件 / 搜内容
execute沙箱后端下执行命令
权限：用 permissions=[FilesystemPermission(...)] 做路径级 allow/deny（如只开 /workspace/**、拒绝 .env）。它约束内置文件工具，可与 HITL 互补。

三个作用

  • 草稿本：笔记、中间结论、报告草稿；
  • 卸载区：大工具结果自动落盘（见第 08 节）；
  • 协作区：主 agent 与子agent通过文件交换大块内容。
07

能力三：子agent与上下文隔离

SubAgents & Context Isolation

当某个子任务会产生大量工具调用、搜索结果或文件内容时，交给 subagent 去做。主 agent 仅接收最终结论，中间过程不进入其上下文。

工作方式

  1. 主 agent 拥有 task 工具（参数：子agent类型 + 任务描述）；
  2. 子agent用自己的新上下文执行，拥有自己的工具与提示词；
  3. 完成后返回一条简洁结果作为 task 的工具结果；
  4. 主 agent 基于结果继续推理。多个 task 调用可以并行。

默认总有一个 general-purpose 子agent：与主 agent 同提示词同工具，用于上下文隔离。

自定义子agent
research_subagent = {
    "name": "research-agent",
    "description": "深入研究单个主题。一次只给它一个主题。",
    "system_prompt": "你是严谨的研究员，最终只输出结论与引用来源。",
    "tools": [internet_search],
    "model": "openai:gpt-5.4-mini",   # 可选：子agent用更便宜的模型
}

agent = create_deep_agent(
    model="openai:gpt-5.4",
    tools=[internet_search],
    system_prompt=RESEARCH_INSTRUCTIONS,
    subagents=[research_subagent],
)
适用场景：研究调研、代码库分析、长文档整理、多方案并行评估。关键技巧：description 决定主 agent 何时调用它，要写清楚“做什么、什么时候用、输入粒度”。
08

能力四：上下文压缩

Offloading & Summarization

即便使用文件系统与子 agent，长会话仍会使上下文持续增长。Deep Agents 内置两种自动压缩机制：

Offloading 解决“单次太大”

一次搜索、一次读文件就可能塞进几万 token。落盘后模型按需分页读取，“用多少读多少”。

Summarization 解决“累积太多”

几十轮之后历史本身就超窗。摘要保留目标、决策、关键事实，让长会话不会因 token 爆掉而中断。
09

上下文工程全景

Context Engineering

综合前述能力，Deep Agents 将上下文分为五类分别管理。

类别放什么谁能看到生命周期
Input context系统提示词、AGENTS.md 记忆、技能描述、工具说明模型每次调用
Runtime contextuser_id、租户、API key、数据库连接工具 / 中间件（可传递给子agent）单次运行
Compression被卸载的大结果、历史摘要模型（按需读取）线程内
Isolation子agent的中间过程仅子agent子任务结束即丢弃
Long-term memory用户偏好、项目约定、研究进度模型（经文件工具）跨线程、跨会话
注意：Runtime context 会传递给子agent，但不会自动暴露给模型。敏感信息（如 API key）应经工具或中间件读取后使用，勿写入提示词。

能力五：长期记忆与 Skills

memory= · skills= · Backend

区分两套机制：memory= / skills= 决定哪些文件注入或披露给模型；CompositeBackend 决定路径路由到哪个存储后端。二者可并用。

from deepagents import create_deep_agent
from deepagents.backends import CompositeBackend, StateBackend, StoreBackend
from langgraph.store.memory import InMemoryStore  # 生产可换平台 Store

store = InMemoryStore()
agent = create_deep_agent(
    model="openai:gpt-5.4",
    memory=["./AGENTS.md"],           # 启动时载入常驻指令/偏好
    skills=["./skills/"],             # 渐进披露：先 frontmatter，用时再读全文
    backend=CompositeBackend(         # 实例 + store=，勿再写 lambda rt
        default=StateBackend(),       # 普通文件：线程内
        routes={"/memories/": StoreBackend(namespace=lambda _rt: ("memories",))},
    ),
    store=store,
)

SKILL.md frontmatter（简例）

---
name: langgraph-docs
description: 需要准确的 LangGraph 指引时使用。
---

# langgraph-docs
先读 docs 索引，再按需拉取相关页面。
注意：把记忆文件放在 /memories/ 下时，路径会走 StoreBackend（跨线程）；本地 ./AGENTS.md 也可直接给 memory=。路径路由 ≠ memory= API。

适合放进长期记忆的内容

偏好 语言、格式、风格
约定 项目规范、命名、目录
进度 研究进行到哪一步
事实 反复用到的关键信息

Memory 与 Skills 怎么分工？

Memory（memory=）Skills（skills=）
内容一直都重要的事按需才用的详细知识 / 流程
加载方式启动时注入系统提示（常驻）启动只给 name/description，用到再读全文
典型形式AGENTS.mdskills/xxx/SKILL.md
代价常驻 token，要精简几乎零常驻成本
原则：持续相关的内容放入 memory=；偶发且篇幅长的内容放入 skills=（渐进式披露）。

人工介入与持久化执行

Human-in-the-loop on LangGraph

长周期 agent 常涉及高风险操作（删文件、发邮件、写数据库）。基于 LangGraph，Deep Agent 支持中断 → 人工审批 → 恢复。路径级 permissions= 可与 HITL 互补：先做声明式路径控制，再对危险工具人工审批。

from deepagents import create_deep_agent, FilesystemPermission
from langgraph.checkpoint.memory import MemorySaver
from langgraph.types import Command

agent = create_deep_agent(
    model="openai:gpt-5.4",
    tools=[send_email, delete_record],
    permissions=[  # 可选：先匹配先生效；先拦 .env，再放行 workspace
        FilesystemPermission(operations=["read", "write"], paths=["/workspace/.env"], mode="deny"),
        FilesystemPermission(operations=["read", "write"], paths=["/workspace/**"], mode="allow"),
        FilesystemPermission(operations=["read", "write"], paths=["/**"], mode="deny"),
    ],
    interrupt_on={
        "send_email": True,                 # 需审批
        "delete_record": {"allowed_decisions": ["approve", "reject"]},
        "write_file": False,                # 不需审批
    },
    checkpointer=MemorySaver(),             # 中断必须有 checkpointer
)

cfg = {"configurable": {"thread_id": "hitl-1"}}
r = agent.invoke({"messages": [("user", "通知客户并清理测试数据")]}, cfg)
print(r["__interrupt__"])                   # 查看待审批的工具调用

# 人工审批后恢复执行
agent.invoke(Command(resume={"decisions": [{"type": "approve"}]}), cfg)

扩展与定制：渐进式工具披露

Custom Middleware

工具数量过多（如 30+）时，工具选择准确率下降，提示词亦被工具说明膨胀。渐进式工具披露：先暴露少量核心工具，再按需逐步开放。

示意代码：用中间件在每次调用模型前过滤工具
from langchain.agents.middleware import AgentMiddleware, ModelRequest

CORE_TOOLS = {"search_tools", "read_file", "write_file", "write_todos", "task"}

class ProgressiveToolsMiddleware(AgentMiddleware):
    def wrap_model_call(self, request: ModelRequest, handler):
        unlocked = set(request.state.get("unlocked_tools", []))   # 由 search_tools 写入 state
        visible = [t for t in request.tools if t.name in CORE_TOOLS | unlocked]
        return handler(request.override(tools=visible))

agent = create_deep_agent(
    model="openai:gpt-5.4",
    tools=all_36_tools + [search_tools],
    middleware=[ProgressiveToolsMiddleware()],
)

中间件常用的钩子：before_model / after_model（改状态）、wrap_model_call（改请求：提示词、工具、模型）、wrap_tool_call（拦截工具执行：鉴权、重试、截断结果）。上面的代码只是示意，state 字段需要配合自定义 state_schema。

心智模型：框架、运行时、Harness

LangChain · LangGraph · Deep Agents

Agent Harness（马具、支架）指“给 agent 提供一整套运行框架和配套能力的外壳”。它不是模型本身，也不只是一段 prompt，而是把 agent 真正跑起来所需的东西打包在一起：

  • 规划与执行循环、工具调用机制
  • 上下文管理、记忆、子agent
  • 流式输出、持久化执行
类比：模型≈发动机；LangChain≈零部件标准；LangGraph≈底盘与传动；Deep Agents≈整车（开箱可跑长任务）。Claude Code、Codex CLI 同属 harness。

什么时候用 Deep Agents？

Decision guide

✓ 适合

  • 复杂任务编排：深度研究、代码修改、报告撰写
  • 需要规划与多轮工具调用（几十到上百步）
  • 需要文件系统、记忆、子agent
  • 需要长时间运行、可中断恢复的 agent

✗ 不太适合

  • 简单单轮问答（徒增延迟与成本）
  • 纯函数式调用 / 结构化抽取
  • 只有一个工具的小型流程
  • 流程固定、强确定性的业务（用 LangGraph 显式建图更合适）

最佳实践与常见坑

Best practices & pitfalls

最佳实践

方面建议
系统提示词写清楚领域流程：何时规划、何时委派、产出写到哪个文件、最终交付格式
子agentdescription 写清“用途 + 时机 + 输入粒度”；要求只回传结论，别回传原始数据
模型分层主 agent 用强模型做规划与综合；子agent可用更便宜、更快的模型
工具工具少而精；返回值精简；工具多时用渐进式披露
记忆memory 保持短小；长知识放 skills 或文件，按需读取
可观测接入 LangSmith，重点看 token 曲线、子agent调用次数、失败的工具调用

常见坑

成本与延迟失控

规划、子 agent、摘要均会额外调用 LLM；简单任务使用 Deep Agent 可能显著增加延迟。应设置递归上限并监控成本。

子 agent 过度委派

主 agent 将过细任务也委派出去，或子 agent 之间重复劳动。应在提示词中给出委派标准与并行上限。

摘要丢失关键信息

重要的约束和决策应该主动写进文件或 todos，不要只依赖消息历史。

安全边界

本地文件系统或沙箱执行后端拥有真实权限，要限定根目录、对危险工具配置 interrupt_on。
