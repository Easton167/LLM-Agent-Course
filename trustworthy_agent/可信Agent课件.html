如何让用户信任你的 AI Agent？

Agent 能调用工具、修改数据、发送邮件、花真金白银。能力越强，用户越要问一句：“我凭什么把这件事交给它？”
这节课不讲怎么让 Agent 更聪明，而讲怎么让用户敢用、会用、愿意一直用——用三根支柱把“黑盒”变成“玻璃盒”，再把“玻璃盒”变成“驾驶舱”。

可解释性 Explainability看得清：它为什么这么做
透明度 Transparency看得全：它能做什么、正在做什么
反馈循环 Feedback Loop管得住：错了我能改、改了它能学
动手实践create_agent + Middleware + LangSmith
01

Agent 落地的最后一公里：信任

Capability ≠ Trust

Chatbot 说错一句话，用户顶多一笑了之；Agent 做错一件事，可能是退错一笔款、删错一张表、发错一封邮件。Agent 从“说”走向“做”，信任就从“锦上添花”变成了“准入门槛”。

关键认知：我们要追求的不是“让用户最大程度地信任 Agent”，而是“校准的信任”——用户对 Agent 的信任程度，恰好等于 Agent 的真实可靠度。可解释性、透明度、反馈循环，都是为这个目标服务的工具。

用户不信任 Agent 的三个根本原因

用户的疑问本质对应支柱
“它为什么给出这个结论？靠谱吗？”决策过程是黑盒，无法验证可解释性
“它到底能干什么？现在在干什么？动了我哪些数据？”能力边界、运行状态、权限不可见透明度
“它要是做错了，我能拦住吗？下次还会错吗？”缺少控制权和改进通道反馈循环
02

可信 Agent 的三根支柱

See it · Know it · Control it

可解释性 ≠ 把思考过程全倒出来

是把结论和依据的关系讲清楚，让用户能验证，而不是让用户读 3000 字的思维链。

透明度 ≠ 把所有日志都甩给用户

是让用户在需要时一定能找到：它做过什么、能动什么、不会什么。

反馈循环 ≠ 加一个点赞按钮

是干预 → 记录 → 改进的闭环。只收不改的反馈，比没有反馈更伤信任。

三者的关系：可解释性让用户判断对不对，透明度让用户预期会发生什么，反馈循环让用户在判断和预期落空时有办法。缺任何一根，信任都立不住。

03

可解释性：解构黑盒决策

Explainability

大模型的内部计算是不可解释的（几百亿参数），但 Agent 的行为是可以解释的：它查了什么、看到了什么、基于哪几条证据、做了哪些假设、得出了什么结论。我们解释的是“行为链路”，不是“神经元”。

分层解释：用户只为自己关心的那一层付出注意力

L1一句话结论 + 核心理由

默认展示，所有用户都看。
“建议全额退款 ¥328。理由：商品签收 3 天内、属于质量问题、符合 7 天无理由政策。”

L2决策依据 + 可点击溯源

一键展开，谨慎的用户看。
订单记录、物流签收时间、退款政策第 3.2 条原文、用户上传的照片——每条都能点开原始数据。

L3完整执行轨迹

面向开发者 / 审计人员。
每一次模型调用、工具调用的入参出参、耗时、Token（LangSmith Trace）。

一个好的解释必须包含的五个要素

要素回答的问题反例（看了更不放心）正例
结论你最终建议什么？“综合考虑多方面因素……”“建议全额退款 ¥328”
推理链路你是怎么一步步得出的？直接甩出结论查订单 → 核对签收时间 → 匹配政策条款 → 判断
依据你凭什么？“根据相关规定”“《退款政策》3.2 条：签收 7 日内……”[1]
假设你默认了什么前提？不说，悄悄默认“假设照片中的破损为运输造成”
置信度你有多确定？所有回答语气同样笃定“置信度：中。照片模糊，建议人工确认”

反模式：把原始思维链（CoT）直接给用户

  • 冗长：用户没耐心读，等于没解释
  • 不忠实：模型写出的“思考”不一定是它真实的决策原因（事后合理化）
  • 泄露：可能把系统提示词、内部规则、其他用户数据带出来

正确做法：结构化、可验证的解释

  • 让模型按 Schema 输出“结论 / 步骤 / 证据 / 假设 / 置信度”
  • 证据必须指向真实的工具返回结果，可点击溯源
  • 解释的价值在于可验证，不在于“看起来很有道理”
04

可解释性落地：结构化解释 + 证据溯源

Structured Output with Evidence

贯穿本课的示例：一个客服退款 Agent，它有两个工具：search_orders（只读查询订单）和 issue_refund（真实打款，不可逆）。

explainable_agent.py — 用 response_format 强制输出“带依据的结论”
from typing import Literal
from pydantic import BaseModel, Field
from langchain.agents import create_agent


class Evidence(BaseModel):
    source: str = Field(description="依据来源，必须是工具名或文档名，如 search_orders / 退款政策3.2")
    content: str = Field(description="从工具返回结果中原样摘录的关键内容，禁止编造")


class ExplainedDecision(BaseModel):
    conclusion: str = Field(description="一句话结论")
    reasoning_steps: list[str] = Field(description="得出结论的关键步骤，3-5 步")
    evidence: list[Evidence] = Field(description="支撑结论的证据")
    assumptions: list[str] = Field(description="结论依赖但未经验证的前提")
    confidence: Literal["高", "中", "低"]
    need_human_review: bool = Field(description="置信度低或涉及资金时为 True")


agent = create_agent(
    model="openai:gpt-4o-mini",
    tools=[search_orders, issue_refund],
    system_prompt="你是退款审核助手。所有结论必须引用工具返回的真实数据；信息不足时直接说明，不要猜测。",
    response_format=ExplainedDecision,
)

result = agent.invoke({"messages": [{"role": "user", "content": "订单 A1024 能退款吗？"}]})
decision: ExplainedDecision = result["structured_response"]

前端如何渲染这份解释

退款审核助手订单 A1024置信度：中
结论建议全额退款 ¥328
推理步骤① 查询订单：已签收 3 天
② 匹配政策：签收 7 日内可无理由退货
③ 核对商品：非定制类，不在例外清单
依据search_orders：signed_at=2026-10-04[1]
退款政策 3.2：“签收之日起 7 日内……”[2]
假设⚠ 假设商品未拆封使用（系统无法验证）
查看完整轨迹 (L3)依据有误

三条工程要点

  • 证据只能来自工具结果。在 Prompt 中要求“原样摘录”，并在后端校验 evidence.content 确实出现在本轮的 ToolMessage 中——校验不过就降级为“低置信度”。
  • 假设要显式化。用户最容易被“隐含假设”坑。把假设单独成栏、用警示色，提醒用户这里需要人来判断。
  • 置信度驱动交互。need_human_review=True 时，前端不展示“执行”按钮，而是“提交人工复核”。解释直接决定了下一步的控制权在谁手里。
RAG 场景同理：回答中的每一句话都挂上引用编号，用户点击即可跳到原文段落。“有出处的回答”比“说得漂亮的回答”可信得多。
05

透明度（上）：坦诚能力边界

Be Honest About Limitations

反直觉的事实：一个会说“我做不到”的 Agent，比一个什么都说“没问题”的 Agent 更值得信任。用户最怕的不是 Agent 不会，而是 Agent 不知道自己不会。

上线前就公开一份“能力说明书”（Agent Card）

维度退款助手的声明示例
能做什么查询订单与物流；根据《退款政策》判断是否可退；在用户确认后发起 ¥1000 以内的退款
不能做什么不能修改订单金额；不能处理跨境订单；不能判断商品真伪；不会在未经确认的情况下打款
已知局限对模糊照片的破损判断准确率较低；政策更新后有 24 小时同步延迟
数据访问读取：订单、物流、退款政策。写入：退款单。不读取：用户支付账户、聊天以外的个人信息
出错时所有退款可在 24 小时内由客服主管撤销；问题反馈入口：对话右上角“报告问题”

运行时：在边界处“主动刹车”

  • 超出能力：“跨境订单我无法处理，已为您转接人工客服。”
  • 信息不足：“订单号未查到，请确认是否为 A 开头的 5 位编号。”
  • 置信度低：“照片无法判断破损原因，建议上传更清晰的照片或转人工。”
  • 超出权限：“该订单 ¥2,680 超过我的审批额度（¥1000），已提交主管审批。”

把“我不知道”写进系统设计，而不是只写进 Prompt

  • 工具返回空结果 → 不允许模型自行补全，直接返回“未找到”
  • 结构化输出中 confidence="低" → 前端强制走人工路径
  • 为“拒答 / 转人工”设计正向体验，不要把它当失败
  • 评估集中专门加入“应该拒答”的用例，检查 Agent 会不会硬答
记住：能力边界说在前面，是承诺；出了事才说，是借口。前者积累信任，后者透支信任。
06

透明度（下）：实时状态、操作流水、底层权限

Status · Audit Log · Permissions

Agent 执行一个任务可能要 30 秒甚至 30 分钟。这段时间里如果界面只有一个转圈的 Loading，用户会焦虑、会怀疑、会刷新页面。让用户随时知道：它在干什么、干到哪了、动了什么。

① 实时状态：流式推送每一步

stream_status.py
for chunk in agent.stream(
    {"messages": [{"role": "user", "content": "处理订单 A1024 的退款"}]},
    config,
    stream_mode="updates",       # 每个节点执行完就推送一次
):
    for node, update in chunk.items():
        if node == "__interrupt__":          # 被 HITL 拦下，等待用户裁决
            push_status("waiting", "等待您确认", update[0].value)
            continue
        if not update:                       # 中间件节点可能没有状态更新
            continue
        msg = update["messages"][-1]
        if node == "model" and msg.tool_calls:
            for tc in msg.tool_calls:
                push_status("running", f"正在调用 {tc['name']}", tc["args"])
        elif node == "tools":
            push_status("done", f"{msg.name} 已返回", msg.content[:80])

② 操作流水：每次工具调用都留痕

audit_middleware.py
import time
from langchain.agents.middleware import wrap_tool_call


@wrap_tool_call
def audit_log(request, handler):
    call = request.tool_call
    start = time.time()
    result = handler(request)          # 真正执行工具
    save_audit({                        # 写入不可篡改的审计表
        "tool": call["name"],
        "args": call["args"],
        "result": str(result.content)[:200],
        "cost_ms": int((time.time() - start) * 1000),
        "thread_id": request.runtime.config["configurable"]["thread_id"],
    })
    return result


agent = create_agent(model, tools, middleware=[audit_log])

用 Middleware 而不是在每个工具里写日志：一处拦截，全部覆盖，新加的工具也不会漏记。

③ 底层权限：大方袒露，最小授权

工具权限类型影响范围是否可撤销执行策略
search_orders只读仅当前用户的订单—自动执行
create_ticket可逆写入新建工单可关闭自动执行，事后通知
issue_refund不可逆写入资金流出 ≤ ¥100024h 内主管可撤销必须用户确认
安全感来自“可预期”：用户在授权前就看到这张表，就知道 Agent 最坏能做到什么程度。最小授权（只给完成任务必需的权限）+ 权限公开，比任何“请放心”的文案都有效。
07

反馈循环（上）：敏捷的干预通道

Human-in-the-Loop

可解释性和透明度让用户“看见”，但如果看见了问题却拦不住，只会更焦虑。干预通道把用户从“观众”变成“法官”：Agent 负责提案，人负责裁决。

不是每一步都要问：按“风险”决定干预强度

影响范围 \ 可逆性可逆（可撤销）部分可逆不可逆
仅影响自己自动执行
草拟回复、查询数据		自动执行 + 事后通知
修改个人设置		执行前确认
删除自己的文件
影响他人 / 外部自动执行 + 事后通知
创建工单		执行前确认
发送邮件、发消息		强确认 + 可编辑参数
打款、删库、提交合同
涉及资金 / 合规执行前确认强确认 + 二次校验多人审批 / 禁止 Agent 执行

每一次确认都有成本。问得太多 → 用户无脑点“同意”（确认疲劳），干预形同虚设；问得太少 → 出事。风险分级就是在两者之间找平衡。

用户手里应该有的四种裁决

需要您确认不可逆 · 涉及资金
操作issue_refund 发起退款
参数订单 A1024 · 金额 ¥328.00 · 原路退回
理由签收 3 天内，符合退款政策 3.2 条
影响资金将在 1–3 个工作日内退回用户账户
批准修改金额拒绝并说明原因我来回答
裁决含义
approve按原计划执行
edit改参数再执行（如把 ¥328 改成 ¥200 部分退款）
reject不执行，并把拒绝原因告诉 Agent，让它调整方案
respond人直接代替工具给出结果（如“已线下处理”）
此外还要有一个“急停按钮”：任何时刻用户都能中断正在运行的任务，并且 Agent 能告诉用户“已经做了哪些、哪些还没做”——这又回到了透明度。
08

干预通道落地：HumanInTheLoopMiddleware

interrupt → decide → resume

LangChain v1 内置了人机协同中间件：在指定工具被调用前暂停整个 Agent，把待执行的操作交给人裁决，裁决后从断点原地恢复。依赖 checkpointer 保存暂停时的状态。

hitl_agent.py
from langchain.agents import create_agent
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import Command

agent = create_agent(
    model="openai:gpt-4o-mini",
    tools=[search_orders, issue_refund],
    middleware=[
        HumanInTheLoopMiddleware(
            interrupt_on={
                "search_orders": False,                                         # 只读：自动执行
                "issue_refund": {"allowed_decisions": ["approve", "edit", "reject"]},  # 资金：必须裁决
            },
            description_prefix="退款操作需要您确认",
        ),
        audit_log,                                    # 上一节的审计中间件，照样生效
    ],
    checkpointer=InMemorySaver(),                     # 生产环境换成 PostgresSaver
)

config = {"configurable": {"thread_id": "refund-A1024"}}
result = agent.invoke({"messages": [{"role": "user", "content": "订单 A1024 退款"}]}, config)

# 1) Agent 在 issue_refund 之前暂停，把待审批的操作抛给前端
if "__interrupt__" in result:
    request = result["__interrupt__"][0].value
    for action in request["action_requests"]:
        print(action["name"], action["args"], action["description"])

# 2) 用户裁决：把金额改成 200 元（部分退款）
result = agent.invoke(
    Command(resume={"decisions": [{
        "type": "edit",
        "edited_action": {"name": "issue_refund", "args": {"order_id": "A1024", "amount": 200}},
    }]}),
    config,                                           # 同一个 thread_id，从断点继续
)

# 也可以拒绝，并告诉 Agent 原因 —— 它会据此调整方案，而不是直接崩掉
# Command(resume={"decisions": [{"type": "reject", "message": "商品已拆封，按政策只能换货"}]})

为什么必须有 checkpointer

暂停可能持续几小时（等主管审批）。状态必须持久化，服务重启后也能从断点恢复。

reject 的 message 很关键

它会作为工具结果回到模型。这就是最短的反馈回路：人的一句纠正，当场改变 Agent 的下一步。

按工具配置，不按 Prompt 约束

“打款前要确认”写在 Prompt 里，模型可能忘；写在 Middleware 里，代码保证一定会停。
09

反馈循环（下）：评价系统与持续进化

Collect → Attribute → Evaluate → Improve

干预解决的是“这一次”不出错，评价系统解决的是“下一次”不再错。用户的每一次点赞、点踩、修改、拒绝，都是免费的标注数据——前提是你真的拿它去改进了。

显式反馈 vs 隐式反馈

类型信号特点
显式点赞/点踩、1–5 分、文字评论、“依据有误”按钮意图明确，但只有不到 5% 的用户会主动给
隐式审批时 edit 了参数、reject、重新提问、复制结果、中途中断、转人工量大、真实，需要定义规则解读

HITL 里的 edit 是最有价值的信号：用户不只说“错了”，还直接给出了正确答案。

把反馈挂到 Trace 上（LangSmith）

import uuid
from langsmith import Client

run_id = uuid.uuid4()
result = agent.invoke(inputs, {**config, "run_id": run_id})

# 用户在界面上点了“踩”，并留言
Client().create_feedback(
    run_id=run_id,
    key="user_rating",
    score=0,
    comment="政策引用错了，跨境订单不适用 3.2 条",
)

反馈和完整执行轨迹绑定后，开发者能直接定位到是哪次检索、哪次工具调用、哪段 Prompt 出了问题，再把这条 Trace 一键加入评估数据集。

人机共生：用户纠正一次，Agent 记住一次（快循环）；一类问题被反复纠正，就沉淀为规则和测试（慢循环）。Agent 越用越懂你，信任随之“复利增长”——这就是“在不断驯化中达成共生”。

综合案例：三根支柱如何在一次交互中协同

Putting It All Together

用户：“订单 A1024 收到的杯子是裂的，帮我退款。”

步骤Agent 的行为用户看到的支柱
1检查请求是否在能力范围内（国内订单 ✓）“我可以帮您处理，预计需要 10 秒”透明度能力边界
2调用 search_orders（只读，自动执行，写入审计）进度条：“正在查询订单… 已签收 3 天”透明度实时状态 · 流水
3匹配政策，生成结构化解释结论 + 3 步推理 + 2 条可点击依据 + “假设：破损非人为”可解释性链路 · 依据 · 假设
4准备调用 issue_refund，被 HITL 中间件拦截确认卡片：¥328 · 不可逆 · 批准 / 修改 / 拒绝反馈循环干预通道
5用户 reject：“只退 200，杯子还能用”→ Agent 改为部分退款方案再次提交新的确认卡片：¥200反馈循环当场纠正
6用户批准，执行退款，返回流水号“已退款 ¥200，流水号 RF-88231，24h 内可撤销”透明度结果可追溯
7记录本次 edit / reject 作为隐式反馈；用户点赞“感谢反馈”反馈循环评价 · 进化
注意第 5 步：Agent 错了吗？没有，它按政策给出了合理建议。但最终决定权在用户手里，而且用户的意见当场改变了 Agent 的行为。用户这时得到的不只是一次退款，而是“这个 Agent 听我的”的确定感——这就是信任的来源。

常见反模式 & 上线前检查清单

Anti-patterns & Checklist

反模式：这些做法正在消耗用户的信任

反模式后果
永远语气笃定，从不说“不确定”第一次出错就信任崩塌
“根据相关资料”——引用无法点开解释沦为装饰
长时间 Loading，没有中间状态焦虑、重复提交
每一步都弹确认框确认疲劳，用户闭眼点同意
安全约束只写在 Prompt 里模型一“忘”就越权
拒绝后 Agent 直接终止或重复同一方案用户觉得“它根本不听”
有点踩按钮，但数据没人看反馈石沉大海，用户不再反馈
出事后才公布能力限制声明变借口

检查清单

可解释性

  • ☐ 结论是否附带推理步骤和可溯源的依据？
  • ☐ 依据是否校验过确实来自工具结果？
  • ☐ 隐含假设和置信度是否显式展示？
  • ☐ 是否提供 L1/L2/L3 分层查看？

透明度

  • ☐ 是否有公开的能力说明书（能做 / 不能做 / 局限）？
  • ☐ 长任务是否流式展示进度？
  • ☐ 每次工具调用是否进入审计日志？
  • ☐ 权限清单是否在授权前可见、是否最小授权？

反馈循环

  • ☐ 高风险工具是否由代码（Middleware）强制拦截？
  • ☐ 用户能否 批准 / 修改 / 拒绝 / 随时中断？
  • ☐ 反馈是否关联到 Trace，并进入评估集？
  • ☐ 是否把“已根据反馈改进”告诉用户？

总结与思考题

Recap
支柱一句话核心手段LangChain 落地
可解释性解构黑盒，让用户看得清、想得通分层解释、证据溯源、假设与置信度response_format 结构化输出
透明度坦诚边界，同步状态，袒露权限能力说明书、流式状态、审计日志、最小授权stream_mode="updates"、@wrap_tool_call
反馈循环人是最终法官，在驯化中共生风险分级干预、四种裁决、双速反馈闭环HumanInTheLoopMiddleware、LangSmith Feedback
一句话带走：用户信任的从来不是“AI 很聪明”，而是“我知道它为什么这么做、知道它会做什么、知道它做错了我能管”。信任不是宣传出来的，是被设计出来、被证据积累出来的。

思考题

  1. 你的 Agent 有一个“发送邮件”工具。按照风险矩阵，它应该自动执行还是需要确认？如果是发给公司内部同事 vs 发给客户，策略应该一样吗？
  2. 模型输出的“推理步骤”可能是事后合理化的。除了在 Prompt 里要求“如实”，你还能用什么工程手段提升解释的可信度？
  3. 用户连续 10 次都直接点“批准”，没有看内容。这说明了什么问题？你会怎么调整？
参考思路
  1. 发邮件“影响他人、不可撤回”。内部邮件可以“执行前确认”，对外邮件建议“强确认 + 可编辑正文”；可以按收件人域名动态配置 interrupt_on。
  2. 校验证据是否真实出现在工具返回中；让解释引用的数据与最终执行参数做一致性检查；用评估集对比“解释”与“行为”是否一致；L3 层直接展示真实工具调用而不是模型自述。
  3. 这是确认疲劳：低风险操作被过度拦截，或确认卡片信息不够醒目。应该下调低风险操作的拦截等级，只在真正关键处确认，并在卡片中突出“金额 / 收件人 / 不可逆”等关键字段。
