## 〇、开场（约 1 分 30 秒）

【画面：封面「如何让用户信任你的 AI Agent？」】

大家好，欢迎回到我们的 LangChain 智能体课程。

前面几节课，我们一直在做一件事：让 Agent 更强。会调工具、会反思、会规划、会做长任务。今天我们换一个角度，问一个更现实的问题：

**Agent 已经很强了，可用户为什么还是不敢用？**

大家想想，如果你公司上线了一个 Agent，它能直接给客户退款、能改数据库、能替你发邮件。你敢不敢让它直接干？大部分人的第一反应是：“等等，我得先看看它要干什么。”

这就是今天的主题：**信任**。

我会用三根支柱来讲：**可解释性**，让用户看得清它为什么这么做；**透明度**，让用户看得全它能做什么、正在做什么；**反馈循环**，让用户管得住——错了能改，改了它能学。

用一句话概括这节课的目标：把 Agent 从一个“黑盒”，变成“玻璃盒”，再变成用户手里的“驾驶舱”。

---

## 一、信任鸿沟（约 3 分钟）

【画面：01 节开头一段话】

先说为什么信任突然变得这么重要。

Chatbot 时代，模型说错一句话，用户笑一笑就过去了。但 Agent 不一样，Agent 是会**动手**的。它可能退错一笔款、删错一张表、发错一封邮件。从“说”到“做”，信任就从加分项变成了**准入门槛**。

【画面：图 1-1 信任校准图】

但是，我要先纠正一个常见误区：**我们的目标不是让用户无限信任 Agent。**

看这张图。横轴是 Agent 的实际可靠度，纵轴是用户的信任程度。中间这条蓝色对角线，叫**校准的信任**——用户有多信任它，恰好等于它有多靠谱。

对角线左上方，红色区域，是**过度信任**：Agent 没那么靠谱，用户却觉得它肯定对。结果就是把幻觉当事实，把越权操作当正常。一次事故，用户就再也不回来了。

右下方，橙色区域，是**信任不足**：Agent 其实挺靠谱，用户却不放心，每个结果都自己重做一遍。那 Agent 省下的时间，全被复核成本吃掉了，最后上线即闲置。

【画面：底部蓝色提示框】

所以请记住今天第一个关键词：**校准的信任**。我们今天讲的所有手段，都是为了让用户的信任**贴着能力走**——能做好的放心交给它，做不好的它自己主动说出来。

【画面：三个原因的表格】

那用户为什么不信任？归根到底是三个疑问：

第一，“它为什么给出这个结论？”——决策是黑盒，没法验证。这对应**可解释性**。

第二，“它能干什么？现在在干什么？动了我哪些数据？”——边界、状态、权限都看不见。这对应**透明度**。

第三，“它要是做错了，我能拦住吗？下次还会错吗？”——没有控制权，也没有改进的通道。这对应**反馈循环**。

## 二、三支柱框架（约 2 分钟）

【画面：02 节，图 2-1 三根支柱】

这张图是整节课的地图。

三根柱子，各自回答用户心里的一个问题。蓝色的**可解释性**，回答“它为什么这么做”，目标是想得通、可验证。橙色的**透明度**，回答“它能做什么、在做什么”，目标是无隐瞒、有安全感。绿色的**反馈循环**，回答“做错了我管得住吗”，目标是让人成为最终的决策法官。

三根柱子一起，撑起底下这一层：校准的信任，最终体现为用户**敢用、会用、一直用**。

【画面：三个小方框】

这里我要提前打三个“预防针”，因为这三个概念特别容易被做歪：

**可解释性，不等于把思考过程全倒出来。** 它是把结论和依据的关系讲清楚，让用户能验证。

**透明度，不等于把所有日志都甩给用户。** 它是让用户在需要的时候一定能找到。

**反馈循环，不等于加一个点赞按钮。** 它是干预、记录、改进的闭环。只收不改，比不收还伤信任。

三者的关系可以这么理解：可解释性让用户**判断**对不对，透明度让用户**预期**会发生什么，反馈循环让用户在判断和预期落空的时候**有办法**。

## 三、可解释性：解构黑盒（约 3 分钟）

【画面：03 节开头 lead 段落】

先讲第一根柱子：可解释性。

有同学可能会说：大模型几百亿参数，本身就是不可解释的，怎么解释？

这里要分清楚：我们解释的不是**神经元**，而是 Agent 的**行为链路**。它查了什么，看到了什么，基于哪几条证据，做了哪些假设，最后得出什么结论。这些是完全可以被记录、被展示、被验证的。

【画面：L1 / L2 / L3 三个方框】

那解释要怎么呈现？我推荐**分层解释**。

**L1**，一句话结论加核心理由，默认展示，所有人都看。比如：“建议全额退款 328 元，理由是签收 3 天内、属于质量问题、符合 7 天无理由政策。”

**L2**，决策依据，一键展开，给谨慎的用户看。订单记录、签收时间、政策原文——每一条都能点开看原始数据。

**L3**，完整执行轨迹，给开发者和审计人员看，就是 LangSmith 里那种每一步调用的入参出参。

分层的意义是：**让每个用户只为自己关心的那一层付出注意力。**

【画面：五要素表格】

一个好的解释，要包含五个要素：结论、推理链路、依据、假设、置信度。

大家重点看“反例”这一列。“综合考虑多方面因素”、“根据相关规定”——这种话说了等于没说，甚至让人更不放心。而“假设”和“置信度”这两项，是最容易被忽略的。很多 Agent 对所有问题都用同样笃定的语气回答，用户根本分不清它哪句是有把握的，哪句是猜的。

【画面：反模式与正确做法两个框】

这里有一个非常常见的反模式：**把模型的原始思维链直接展示给用户。**

问题有三个。第一，太长，用户不看，等于没解释。第二，**不忠实**——研究发现，模型写出来的“思考过程”，不一定是它真实的决策原因，很多时候是事后合理化。第三，可能泄露系统提示词或者内部规则。

正确的做法是：**结构化、可验证的解释**。让模型按 Schema 输出，证据必须指向真实的工具返回结果。记住这句话：**解释的价值在于可验证，不在于看起来很有道理。**

## 四、可解释性：代码实现（约 3 分钟）

【画面：04 节代码块】

好，落到代码。我们这节课贯穿一个例子：**客服退款 Agent**。它有两个工具，`search_orders` 只读查询订单，`issue_refund` 真实打款，不可逆。

实现可解释性，最直接的手段就是 `create_agent` 的 `response_format` 参数。

我们定义一个 `ExplainedDecision` 模型：结论、推理步骤、证据列表、假设列表、置信度，还有一个 `need_human_review`，是否需要人工复核。

注意 `Evidence` 的 Field 描述：来源必须是工具名或文档名，内容必须是从工具结果中**原样摘录**，禁止编造。系统提示词里也强调：信息不足就直说，不要猜。

调用之后，从 `result["structured_response"]` 里拿到的就是一个类型安全的对象，前端可以直接渲染。

【画面：左侧 UI 模拟卡片】

看左边这个界面示意：右上角是置信度标签，下面依次是结论、推理步骤、依据（带引用编号，可点击溯源），以及用警示色标出的“假设”——“假设商品未拆封使用，系统无法验证”。用户一眼就知道，**这里是需要我来判断的地方。**

【画面：右侧三条工程要点】

三个工程要点：

第一，**证据只能来自工具结果**。光靠 Prompt 要求还不够，后端最好校验一下，证据内容是否真的出现在这一轮的工具返回里。校验不过，就自动降级成低置信度。

第二，**假设要显式化**。用户最容易被隐含假设坑。

第三，**置信度驱动交互**。当 `need_human_review` 为真时，前端不显示“执行”按钮，而是“提交人工复核”。你看，**解释直接决定了下一步的控制权在谁手里**——这已经和后面的反馈循环连起来了。

RAG 场景也是一样的道理：每句话挂上引用编号，点一下就能跳到原文。有出处的回答，比说得漂亮的回答可信得多。

## 五、透明度：坦诚能力边界（约 2 分 30 秒）

【画面：05 节 lead 段落】

第二根柱子，透明度。先讲上半部分：**坦诚能力边界**。

我先说一个反直觉的事实：**一个会说“我做不到”的 Agent，比一个什么都说“没问题”的 Agent 更值得信任。** 用户最怕的不是 Agent 不会，而是 Agent **不知道自己不会**。

【画面：Agent Card 表格】

所以我建议，上线之前就公开一份“能力说明书”，我们叫它 Agent Card。

它要写清楚五件事：能做什么、不能做什么、已知局限、访问哪些数据、出错了怎么办。

大家注意“不能做什么”里有一句：**不会在未经确认的情况下打款**。还有“数据访问”里明确写了“不读取用户支付账户”。这些话对用户来说就是定心丸。

【画面：两个方框】

光有说明书不够，运行时还要在边界处**主动刹车**。左边四个例子：超出能力就转人工；信息不足就请用户补充；置信度低就建议复核；超出权限就提交审批。

右边更重要：**把“我不知道”写进系统设计，而不是只写进 Prompt。** 工具返回空，就不许模型自己补；置信度低，前端强制走人工路径；拒答和转人工要设计成正向体验，不要当成失败；评估集里专门放一些“应该拒答”的用例，测它会不会硬答。

最后送大家一句话：**能力边界说在前面，是承诺；出了事才说，是借口。**

## 六、透明度：状态、流水、权限（约 3 分钟）

【画面：06 节开头】

透明度的下半部分，是三件事：实时状态、操作流水、底层权限。

Agent 跑一个任务可能要几十秒甚至几十分钟。如果界面只有一个转圈的 Loading，用户就会焦虑、怀疑，甚至反复刷新、重复提交。

【画面：左侧代码 stream_status.py 与进度面板】

第一件事，**实时状态**。用 `agent.stream`，`stream_mode` 设为 `"updates"`，每个节点执行完就推送一次。模型节点发起了工具调用，我们就推“正在调用某某工具”；工具节点返回了，就推“已返回”。

这里有两个细节要注意。一是中间件也会作为节点出现在流里，它们可能没有状态更新，返回的是 None，要跳过。二是当 Agent 被人工审批拦下时，流里会出现一个 `__interrupt__`，这时候就推“等待您确认”。

下面这个进度面板就是效果：每一步有时间、有状态标签，最后一步是橙色的“待确认”。用户看得清清楚楚：它做到哪了，卡在哪了，为什么卡。

【画面：右侧代码 audit_middleware.py】

第二件事，**操作流水**。我们用 `@wrap_tool_call` 写一个审计中间件：在工具执行前后包一层，把工具名、参数、结果摘要、耗时、会话 ID 写进审计表。

为什么用中间件，而不是在每个工具里写日志？因为**一处拦截，全部覆盖**。以后新增工具，也不会漏记。

【画面：权限表格】

第三件事，**底层权限**。看这张表：每个工具是只读、可逆写入还是不可逆写入，影响范围多大，能不能撤销，执行策略是什么。

`issue_refund` 是不可逆写入，影响资金，所以**必须用户确认**。

安全感来自哪里？来自**可预期**。用户在授权之前就看到这张表，就知道 Agent 最坏能做到什么程度。**最小授权加权限公开**，比任何“请您放心”的文案都管用。

## 七、反馈循环：干预通道（约 3 分钟）

【画面：07 节 lead 段落】

第三根柱子，反馈循环。

前两根柱子让用户“看见”了。但如果看见了问题却拦不住，用户只会更焦虑。**干预通道，是把用户从“观众”变成“法官”**：Agent 负责提案，人负责裁决。

【画面：风险矩阵表格】

但是注意，不是每一步都要问。这张风险矩阵，纵轴是影响范围，横轴是可逆性。

只影响自己、可逆的，比如查数据、草拟回复，直接自动执行。影响他人、不可逆的，比如打款、删库，就要强确认，而且允许用户编辑参数。涉及资金合规又不可逆的，甚至要多人审批，或者干脆不让 Agent 执行。

为什么要分级？因为每次确认都有成本。**问得太多，用户就会无脑点“同意”**，这叫确认疲劳，干预就形同虚设了。问得太少，就会出事。

【画面：确认卡片与四种裁决表格】

左边是一个确认卡片的示意：操作、参数、理由、影响，一目了然。下面四个按钮，对应用户手里应该有的**四种裁决**：

**approve**，批准，按原计划执行。
**edit**，修改参数再执行，比如把 328 改成 200，部分退款。
**reject**，拒绝，并且把原因告诉 Agent，让它调整方案。
**respond**，人直接代替工具给出结果，比如“这单我已经线下处理了”。

另外，一定要有一个**急停按钮**：任何时候都能中断任务，而且 Agent 要能告诉用户已经做了哪些、哪些还没做。

## 八、反馈循环：HITL 代码实现（约 3 分钟）

【画面：08 节代码 hitl_agent.py】

这四种裁决，在 LangChain v1 里是内置的，叫 `HumanInTheLoopMiddleware`。

看配置：`interrupt_on` 是一个字典，按工具配置。`search_orders` 设为 False，自动执行；`issue_refund` 允许 approve、edit、reject 三种裁决。上一节的审计中间件也一起挂上，照样生效。

还有一个必不可少的东西：**checkpointer**。演示用 `InMemorySaver`，生产环境请换成 PostgresSaver 这类持久化的。

运行流程分两步。

第一步，正常 invoke。当 Agent 准备调用 `issue_refund` 时，中间件会把整个 Agent **暂停**，返回结果里会带一个 `__interrupt__`，里面是待审批的操作：工具名、参数、描述。前端拿去渲染确认卡片。

第二步，用户做出裁决之后，用 `Command(resume=...)` 再 invoke 一次，传入 decisions。这里演示的是 edit，把金额改成 200。注意，**一定要用同一个 thread_id**，Agent 才能从断点原地继续。

最下面注释里是 reject 的写法，带一个 message：“商品已拆封，按政策只能换货”。

【画面：底部三个方框】

三个要点：

第一，为什么必须有 checkpointer？因为暂停可能持续几个小时，比如等主管审批。服务重启了也要能恢复。

第二，**reject 的 message 非常关键**。它会作为工具结果回到模型里，模型据此调整方案。这是**最短的反馈回路**：人的一句话，当场改变 Agent 的下一步。

第三，**按工具配置，而不是靠 Prompt 约束**。“打款前要确认”写在 Prompt 里，模型可能会忘；写在中间件里，**代码保证它一定会停**。这一点请大家务必记住。

## 九、反馈循环：评价与进化（约 3 分钟）

【画面：09 节 lead 段落】

干预解决的是“这一次”不出错；评价系统解决的是“下一次”不再错。

用户的每一次点赞、点踩、修改、拒绝，都是免费的标注数据。但前提是：**你真的拿它去改进了。**

【画面：图 9-1 双速反馈闭环】

看这张图，这是一个五步闭环：用户交互、收集反馈、归因定位、沉淀评估集、改进发布，然后回到用户交互。

我把它分成两个速度。

上面绿色虚线，是**快循环**，秒级的。用户纠正了一次，比如“我们公司跨境订单不适用这条政策”，直接写进这个用户或这个团队的长期记忆，下一次当场生效。

下面蓝色实线，是**慢循环**，天级或周级的。差评案例沉淀成评估集，改了 Prompt、工具或者路由之后，先跑评估集，确认不退化再上线。

最底下一行小字也很重要：**告诉用户“您上次反馈的问题已经修复了”**。让用户看见自己的反馈是有用的，他才会继续反馈。

【画面：左侧显式 vs 隐式反馈表格】

反馈分两类。显式反馈，就是点赞、打分、评论，意图明确，但愿意主动给的用户通常很少。隐式反馈，是用户的行为：审批时改了参数、拒绝了、重新问了一遍、中途中断、转了人工。量大，也更真实。

这里我特别强调：HITL 里的 **edit 是最有价值的信号**。用户不只是告诉你“错了”，还直接给了你**正确答案**。

【画面：右侧 LangSmith 代码】

技术上，怎么把反馈和执行过程关联起来？用 LangSmith。调用 Agent 时在 config 里传一个 `run_id`，用户点踩的时候，调用 `create_feedback`，传入同一个 run_id、评分和评论。

这样，开发者在 LangSmith 里就能直接看到：这条差评对应的是哪一次检索、哪一次工具调用、哪一段 Prompt 出了问题，然后一键把这条 Trace 加入评估数据集。

【画面：底部提示框】

这就是课题里说的“**在不断驯化中达成共生**”：用户纠正一次，Agent 记住一次；一类问题反复被纠正，就沉淀为规则和测试。Agent 越用越懂你，信任就像复利一样增长。

## 十、综合案例（约 2 分 30 秒）

【画面：10 节表格】

最后我们用一个完整的例子，把三根柱子串起来。

用户说：“订单 A1024 收到的杯子是裂的，帮我退款。”

第一步，Agent 先检查请求在不在能力范围内，是国内订单，可以处理，并告诉用户大概要多久。这是**透明度**里的能力边界。

第二步，调用 `search_orders`，只读，自动执行，同时写入审计日志。用户看到进度：正在查询、已签收 3 天。这是**透明度**里的实时状态和操作流水。

第三步，匹配政策，给出结构化解释：结论、三步推理、两条可点击的依据，还有一条假设。这是**可解释性**。

第四步，准备调用 `issue_refund`，被中间件拦下，弹出确认卡片。这是**反馈循环**里的干预通道。

第五步，用户拒绝了：“只退 200 就行，杯子还能用。”Agent 收到这句话，改成部分退款，再次提交确认。

第六步，用户批准，执行退款，返回流水号，并且告诉用户 24 小时内可撤销。

第七步，这次的修改和拒绝被记录为隐式反馈，用户还点了个赞。

【画面：底部提示框】

请大家特别注意第五步。Agent 错了吗？没有，它按政策给的建议完全合理。但是最终决定权在用户手里，而且用户的一句话**当场**改变了 Agent 的行为。

用户这时候得到的，不只是一次退款，而是一种确定感：**“这个 Agent 听我的。”** 这，就是信任真正的来源。

## 十一、反模式与检查清单（约 2 分钟）

【画面：11 节左侧反模式表格】

我们快速过一遍常见的反模式，这些做法都在悄悄消耗用户的信任。

永远语气笃定，第一次出错就崩塌。引用点不开，解释沦为装饰。长时间 Loading，用户焦虑。每步都弹确认框，用户闭眼点同意。安全约束只写在 Prompt 里，模型一忘就越权。拒绝之后 Agent 直接罢工或者原样再提交一次，用户会觉得它根本不听。有点踩按钮但没人看数据，用户就不再反馈了。还有，出了事才公布能力限制，声明就变成了借口。

## 十二、总结与思考题（约 1 分 30 秒）

【画面：12 节总结表格】

最后总结一下。

**可解释性**：解构黑盒，让用户看得清、想得通。手段是分层解释、证据溯源、假设和置信度，落地用 `response_format`。

**透明度**：坦诚边界、同步状态、袒露权限。手段是能力说明书、流式状态、审计日志、最小授权，落地用 `stream` 和 `wrap_tool_call`。

**反馈循环**：人是最终法官，在驯化中共生。手段是风险分级、四种裁决、双速闭环，落地用 `HumanInTheLoopMiddleware` 和 LangSmith Feedback。

【画面：蓝色提示框】

如果这节课你只记住一句话，我希望是这句：

**用户信任的从来不是“AI 很聪明”，而是“我知道它为什么这么做，知道它会做什么，知道它做错了我能管”。** 信任不是宣传出来的，是被设计出来、被证据一点一点积累出来的。

【画面：思考题】

留三道思考题给大家：

第一，你的 Agent 有一个“发邮件”的工具，它该自动执行还是需要确认？发给同事和发给客户，策略一样吗？

第二，模型输出的推理步骤可能是事后合理化的。除了 Prompt，你还能用什么工程手段让解释更可信？

第三，如果用户连续十次都直接点“批准”，根本不看内容，这说明了什么？你会怎么改？
